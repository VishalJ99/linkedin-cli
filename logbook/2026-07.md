## 2026-07-14 — PER-379 dashboard asset recovery

### Objective

Resolve the raw, non-interactive production dashboard shown after invite login
and close the Railway backup-plan decision.

### Method

- Compared the screenshot with the committed templates and CSS.
- Probed the deployed CSS and JavaScript endpoints directly.
- Inspected the rendered production HTML for its asset URLs.
- Added a regression test requiring same-origin root-relative asset paths.

### Observations

- `/static/app.css` and `/static/app.js` each returned `200` when requested
  directly.
- Railway terminates HTTPS before the application, while Jinja's `url_for`
  observed the untrusted internal HTTP scheme and emitted `http://` asset URLs.
- Chrome blocked those mixed-content URLs. The CSS did not render, and the
  dashboard JavaScript never ran, leaving `Preparing connector…` disabled.
- The user approved retaining the Railway volume while proceeding without the
  paid managed-backup feature. The accepted risk is recorded in
  `decisions/human/PER-379-railway-backups.md`.

### Interpretation

The screenshot was caused by proxy-sensitive static URL generation, not a
missing build artifact. Root-relative asset paths preserve the browser's HTTPS
origin and avoid depending on proxy-header trust for static resources.

### Next steps

1. Deploy the exact asset-fix commit and verify that rendered HTML contains
   `/static/app.css` and `/static/app.js` with no HTTP asset URL.
2. Reload the dashboard and verify the styled responsive layout.
3. Side-load `extension/` from that same commit, then perform the explicit
   consented pairing and first probe under the immediate-stop rule.
