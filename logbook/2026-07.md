## 2026-07-14 — PER-379 dashboard asset recovery

### Objective

Resolve the raw, non-interactive production dashboard shown after invite login
and close the Railway backup-plan decision.

### Method

- Compared the screenshot with the committed templates and CSS.
- Probed the deployed CSS and JavaScript endpoints directly.

- Added a regression test requiring same-origin root-relative asset paths.

### Observations

- `/static/app.css` and `/static/app.js` each returned `200` when requested
  directly.
- Railway terminates HTTPS before the application, while Jinja's `url_for`
  observed the untrusted internal HTTP scheme and emitted `http://` asset URLs.
- Chrome blocked those mixed-content URLs. The CSS did not render, and the
  dashboard JavaScript never ran, leaving `Preparing connector…` disabled.
- The user approved retaining the Railway volume while proceeding without the
  paid managed-backup feature. The accepted risk is recorded in
  `decisions/human/PER-379-railway-backups.md`.

### Interpretation

The screenshot was caused by proxy-sensitive static URL generation, not a
missing build artifact. Root-relative asset paths preserve the browser's HTTPS
origin and avoid depending on proxy-header trust for static resources.

## 2026-07-17 — PER-379 Chrome 150 connector handshake recovery

### Objective

### Method

- Reproduced the connector handshake against Google Chrome
  `150.0.7871.128` using an isolated headless `about:blank` profile.
- Captured only the non-secret WebSocket status and validation outcomes; no
  LinkedIn URL or user Chrome profile was used.
- Added a regression fixture for Chromium's observed status line, confirmed it
  failed against the deployed implementation, then changed only the HTTP status
  parsing.
- Retained validation of HTTP/1.1, numeric status `101`, the `Upgrade` and
  `Connection` headers, and the cryptographic `Sec-WebSocket-Accept` value.

- Ran the complete test/lint/syntax suite, committed and pushed the fix, then
  deployed and inspected a new token-bound connector package in memory.

### Observations

- Chrome returned `HTTP/1.1 101 WebSocket Protocol Handshake`; the previous
  client required the exact non-semantic reason phrase `Switching Protocols`.
  All required upgrade headers and the accept hash were valid.
- The new regression failed before the fix and passed after it.
- All 226 tests passed; Ruff, Python compilation, JavaScript syntax, and diff
  checks passed.
- The patched client upgraded successfully and executed a CDP command against
  Chrome 150 on `about:blank`.
- Commit `d6961d0` was pushed. Railway deployment
  `da8e069b-ab13-4067-a3d2-0f93b645cf5f` reached `SUCCESS` using the Dockerfile
